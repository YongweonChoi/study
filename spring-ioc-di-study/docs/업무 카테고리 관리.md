# 업무 카테고리 관리 — Spring IoC / DI 학습 예제

Spring의 **IoC(제어의 역전)** 와 **DI(의존성 주입)** 를 이론이 아니라 실제 동작하는 코드로 익히기 위한 학습용 예제 문서입니다.

`React 화면 → Spring Controller → Service → MyBatis Mapper → MariaDB` 전 구간을 하나의 기능("업무 카테고리 관리")으로 연결해, 스프링이 `Controller`·`Service`·`Mapper` 객체를 **직접 생성하고 서로 연결해 주는** 지점을 눈으로 확인하는 것이 목표입니다.

| 구분 | 기술 스택 |
| --- | --- |
| Frontend | React + TypeScript + MobX + Tailwind CSS |
| Backend | Spring Boot + MyBatis + Lombok + Java 17 |
| Database | MariaDB |

호출 흐름 요약:
```text
React
  ↓ HTTP
CategoryController
  ↓ DI
CategoryService
  ↓ DI
CategoryMapper
  ↓
MariaDB
```

## 2. 이 프로젝트에서 배우는 IoC / DI

일반적인 Java라면 다음처럼 객체를 직접 생성합니다.

```java
CategoryMapper mapper = new CategoryMapper();

CategoryService service =
        new CategoryServiceImpl(mapper);

CategoryController controller =
        new CategoryController(service);
```

문제는 **객체 생성 책임이 개발자 코드에 있다는 것**입니다.

스프링에서는 이렇게 하지 않습니다.

```java
@RestController
@RequiredArgsConstructor
public class CategoryController {

    private final CategoryService categoryService;
}
```

`new CategoryServiceImpl()`이 없습니다. 그런데도 프로그램이 동작합니다.

스프링이 객체를 만들고,

```text
Spring Container
        │
        ├─ CategoryController Bean
        │
        ├─ CategoryServiceImpl Bean
        │
        └─ CategoryMapper Bean
```

서로 연결해 주기 때문입니다.

```text
CategoryController
        │
        │ DI
        ▼
CategoryServiceImpl
        │
        │ DI
        ▼
CategoryMapper
```

이것이 **IoC와 DI**입니다.

### 4.6 MyBatis Mapper — `CategoryMapper.java`

```java
package com.example.iocdi.mapper;

import com.example.iocdi.domain.Category;
import com.example.iocdi.dto.CategoryRequest;
import org.apache.ibatis.annotations.Mapper;

import java.util.List;

@Mapper
public interface CategoryMapper {

    List<Category> findAll();

    Category findById(Long categoryId);

    int insert(CategoryRequest request);

    int delete(Long categoryId);
}
```

여기가 IoC를 이해할 때 상당히 재미있는 부분입니다.

우리는 `public interface CategoryMapper`만 작성했고, `CategoryMapperImpl.java` 같은 **구현 클래스가 없습니다.** 그런데도 다음 DI가 가능합니다.

```java
private final CategoryMapper categoryMapper;
```

MyBatis가 실행 시점에 **Proxy 객체를 생성해서 Spring Bean으로 등록**하기 때문입니다.

```text
CategoryMapper interface

        ↓

MyBatis

        ↓

Proxy 객체 생성

        ↓

Spring Container 등록

        ↓

CategoryServiceImpl에 DI
```

### 4.7 MyBatis XML — `CategoryMapper.xml`

```xml
<?xml version="1.0" encoding="UTF-8" ?>

<!DOCTYPE mapper
        PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "https://mybatis.org/dtd/mybatis-3-mapper.dtd">

<mapper namespace="com.example.iocdi.mapper.CategoryMapper">

    <select id="findAll"
            resultType="com.example.iocdi.domain.Category">

        SELECT
              category_id
            , category_name
            , description
            , use_yn
            , created_at
        FROM tb_category
        ORDER BY category_id DESC

    </select>


    <select id="findById"
            parameterType="long"
            resultType="com.example.iocdi.domain.Category">

        SELECT
              category_id
            , category_name
            , description
            , use_yn
            , created_at
        FROM tb_category
        WHERE category_id = #{categoryId}

    </select>


    <insert id="insert"
            parameterType="com.example.iocdi.dto.CategoryRequest">

        INSERT INTO tb_category
        (
              category_name
            , description
            , use_yn
            , created_at
        )
        VALUES
        (
              #{categoryName}
            , #{description}
            , 'Y'
            , NOW()
        )

    </insert>


    <delete id="delete"
            parameterType="long">

        DELETE
        FROM tb_category
        WHERE category_id = #{categoryId}

    </delete>

</mapper>
```

### 4.8 Service Interface — `CategoryService.java`

IoC/DI 학습을 위해 일부러 Service를 Interface와 구현체로 분리합니다.

```java
package com.example.iocdi.service;

import com.example.iocdi.domain.Category;
import com.example.iocdi.dto.CategoryRequest;

import java.util.List;

public interface CategoryService {

    List<Category> getCategories();

    Category getCategory(Long categoryId);

    void createCategory(CategoryRequest request);

    void deleteCategory(Long categoryId);
}
```

#### 왜 Interface를 사용하는가?

현재 구조는 다음과 같습니다.

```text
CategoryController
        ↓
CategoryService
        ↑
CategoryServiceImpl
```

Controller는 구현 클래스에 직접 의존하지 않습니다. 다음이 **아니라**,

```java
private final CategoryServiceImpl categoryService;
```

다음처럼 작성합니다.

```java
private final CategoryService categoryService;
```

그래서 구현체를 바꿀 수 있습니다.

```java
@Service
public class CategoryServiceImpl
        implements CategoryService {
}
```

대신 다른 구현체가 있을 수도 있습니다.

```java
public class MockCategoryService
        implements CategoryService {
}
```

Controller 코드에는 변화가 없습니다. 이것이 객체지향의 **DIP(Dependency Inversion Principle)** 와 연결됩니다.

### 4.9 Service 구현체 — `CategoryServiceImpl.java`

```java
package com.example.iocdi.service;

import com.example.iocdi.domain.Category;
import com.example.iocdi.dto.CategoryRequest;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
@RequiredArgsConstructor
public class CategoryServiceImpl implements CategoryService {

    private final CategoryMapper categoryMapper;

    @Override
    public List<Category> getCategories() {

        return categoryMapper.findAll();
    }

    @Override
    public Category getCategory(Long categoryId) {

        return categoryMapper.findById(categoryId);
    }

    @Override
    public void createCategory(CategoryRequest request) {

        categoryMapper.insert(request);
    }

    @Override
    public void deleteCategory(Long categoryId) {

        categoryMapper.delete(categoryId);
    }
}
```

여기가 **DI 학습의 핵심 코드**입니다.

```java
@Service
@RequiredArgsConstructor
public class CategoryServiceImpl implements CategoryService {

    private final CategoryMapper categoryMapper;
}
```

개발자는 다음 코드를 작성하지 않았습니다.

```java
CategoryMapper categoryMapper =
        new CategoryMapper();
```

Spring이 넣어 줍니다. 실제로 Lombok은 다음 생성자를 만들어 줍니다.

```java
public CategoryServiceImpl(
        CategoryMapper categoryMapper
) {
    this.categoryMapper = categoryMapper;
}
```

그리고 Spring이 호출합니다. 개념적으로:

```java
CategoryMapper mapper =
        SpringContainer.getBean(CategoryMapper.class);

CategoryServiceImpl service =
        new CategoryServiceImpl(mapper);
```

이것이 **Constructor Injection**입니다.

### 4.10 Controller — `CategoryController.java`

```java
package com.example.iocdi.controller;

import com.example.iocdi.domain.Category;
import com.example.iocdi.dto.CategoryRequest;
import com.example.iocdi.service.CategoryService;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/categories")
@RequiredArgsConstructor
@CrossOrigin(origins = "http://localhost:5173")
public class CategoryController {

    private final CategoryService categoryService;

    @GetMapping
    public List<Category> getCategories() {

        return categoryService.getCategories();
    }

    @GetMapping("/{categoryId}")
    public Category getCategory(
            @PathVariable Long categoryId
    ) {

        return categoryService.getCategory(categoryId);
    }

    @PostMapping
    public void createCategory(
            @RequestBody CategoryRequest request
    ) {

        categoryService.createCategory(request);
    }

    @DeleteMapping("/{categoryId}")
    public void deleteCategory(
            @PathVariable Long categoryId
    ) {

        categoryService.deleteCategory(categoryId);
    }
}
```

여기도 같은 구조입니다.

```java
private final CategoryService categoryService;
```

`new CategoryServiceImpl(...)`을 하지 않았지만, Spring Container가 자동으로 찾아서 넣습니다.

### 4.11 현재까지의 IoC Container 상태

애플리케이션 실행 후 개념적으로 다음 상태가 됩니다.

```text
┌─────────────────────────────────────────┐
│          Spring IoC Container           │
│                                         │
│                                         │
│   CategoryController Bean               │
│           │                             │
│           │ DI                          │
│           ▼                             │
│   CategoryServiceImpl Bean              │
│           │                             │
│           │ DI                          │
│           ▼                             │
│   CategoryMapper Proxy Bean             │
│                                         │
└─────────────────────────────────────────┘
```

한 문장으로 표현하면:

> 객체를 개발자가 직접 생성하고 연결하지 않고, Spring Container가 객체의 생성과 의존관계를 관리한다.

import axios from "axios";
import type {
  Category,
  CategoryCreateRequest,
} from "../types/category";

const apiClient = axios.create({
  baseURL: "http://localhost:8080/api",
  headers: {
    "Content-Type": "application/json",
  },
});

export const categoryApi = {

  async getCategories(): Promise<Category[]> {

    const response =
      await apiClient.get<Category[]>("/categories");

    return response.data;
  },


  async createCategory(
    request: CategoryCreateRequest
  ): Promise<void> {

    await apiClient.post(
      "/categories",
      request
    );
  },


  async deleteCategory(
    categoryId: number
  ): Promise<void> {

    await apiClient.delete(
      `/categories/${categoryId}`
    );
  },
};

### 5.4 MobX Store — `stores/CategoryStore.ts`

```typescript
import {
  makeAutoObservable,
  runInAction,
} from "mobx";

import { categoryApi } from "../api/categoryApi";

import type {
  Category,
  CategoryCreateRequest,
} from "../types/category";


export class CategoryStore {

  categories: Category[] = [];

  loading = false;

  errorMessage = "";


  constructor() {

    makeAutoObservable(this);
  }


  async fetchCategories() {

    this.loading = true;
    this.errorMessage = "";

    try {

      const data =
        await categoryApi.getCategories();

      runInAction(() => {

        this.categories = data;

      });

    } catch (error) {

      runInAction(() => {

        this.errorMessage =
          "카테고리를 조회하는 중 오류가 발생했습니다.";

      });

    } finally {

      runInAction(() => {

        this.loading = false;

      });
    }
  }


  async createCategory(
    request: CategoryCreateRequest
  ) {

    await categoryApi.createCategory(request);

    await this.fetchCategories();
  }


  async deleteCategory(
    categoryId: number
  ) {

    await categoryApi.deleteCategory(categoryId);

    await this.fetchCategories();
  }
}
```

## 7. IoC와 DI 개념 정리

둘을 혼동하는 경우가 많으므로 나누어 정리합니다.

### 7.1 IoC — Inversion of Control (제어의 역전)

일반 Java에서는 개발자가 객체 생성을 제어합니다.

```java
CategoryService service =
        new CategoryServiceImpl();
```

Spring에서는 Spring이 객체를 생성합니다.

```java
@Service
public class CategoryServiceImpl {
}
```

즉, 객체 생성 권한이 이동합니다.

```text
객체 생성 권한

기존

개발자
  ↓
new

Spring

Spring Container
  ↓
Bean 생성
```

제어권이 개발자에서 프레임워크로 넘어갔기 때문에 **제어의 역전**이라고 합니다.

### 7.2 DI — Dependency Injection (의존성 주입)

다음 객체를 봅시다.

```java
@Service
@RequiredArgsConstructor
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;
}
```

`CategoryServiceImpl`은 업무를 수행하기 위해 `CategoryMapper`가 필요합니다.

```text
CategoryServiceImpl
        │
        │ 의존한다
        ▼
CategoryMapper
```

그 객체를 Spring이 넣어 줍니다.

```text
Spring Container

CategoryMapper Bean
        │
        │ 주입
        ▼
CategoryServiceImpl
```

그래서 Dependency Injection입니다.

### 7.3 IoC와 DI의 관계

```text
IoC
│
│ Spring이 객체 관리
│
└──────────────┐
               │
               ▼
              DI
               │
               │ 필요한 객체를 넣어줌
               ▼
Controller → Service → Mapper
```

> IoC가 더 큰 개념이고, DI는 IoC를 구현하는 대표적인 방법입니다.

### 7.4 Bean이란

이번 예제에서 Spring이 관리하는 객체는 대략 다음과 같습니다.

```text
ApplicationContext
│
├── categoryController
│
├── categoryServiceImpl
│
├── categoryMapper
│
├── dataSource
│
├── sqlSessionFactory
│
└── ...
```

이처럼

> Spring IoC Container가 생성하고 관리하는 객체

를 **Bean**이라고 부릅니다. 관계를 연결하면:

```text
IoC Container
     │
     │ 관리
     ▼
    Bean
     │
     │ 연결 방법
     ▼
     DI
```

### 7.5 용어 대응표

Spring을 처음 배울 때 `DI = @Autowired`처럼 설명하는 경우가 많은데, 이는 정확하지 않습니다. 더 정확하게 정리하면 다음과 같습니다.

```text
IoC
=
객체의 생성/관리 책임을
ApplicationContext가 갖는다.


DI
=
IoC Container가 관리하는 객체들을
필요한 다른 객체에게 연결한다.


Bean
=
IoC Container가 관리하는 객체다.


@Autowired
=
DI를 요청할 수 있는 여러 방법 중 하나다.


@RequiredArgsConstructor
=
Lombok이 생성자를 만들어 주고,
Spring이 그 생성자를 이용해 DI한다.
```

## 8. 의존성 주입 방식 비교

### 8.1 `@RequiredArgsConstructor`를 제거하면?

현재 코드는 다음과 같습니다.

```java
@Service
@RequiredArgsConstructor
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;
}
```

Lombok을 사용하지 않으면 이렇게 됩니다.

```java
@Service
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;


    public CategoryServiceImpl(
            CategoryMapper categoryMapper
    ) {

        this.categoryMapper =
                categoryMapper;
    }
}
```

Spring에서는 생성자가 하나인 경우 `@Autowired`도 필요 없습니다. 즉 다음으로 충분합니다.

```java
public CategoryServiceImpl(
        CategoryMapper categoryMapper
) {
    this.categoryMapper =
            categoryMapper;
}
```

Spring이 다음을 수행합니다.

```text
CategoryMapper 타입 Bean이 있나?

        ↓

있음

        ↓

생성자 parameter로 전달
```

### 8.2 Field Injection vs Constructor Injection

초보 단계에서 흔히 보는 코드입니다.

```java
@Service
public class CategoryServiceImpl
        implements CategoryService {

    @Autowired
    private CategoryMapper categoryMapper;
}
```

작동은 하지만, 실무에서는 생성자 주입을 권장합니다.

```java
@Service
@RequiredArgsConstructor
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;
}
```

차이는 다음과 같습니다.

| 구분 | Field Injection | Constructor Injection |
| --- | --- | --- |
| 방식 | `@Autowired` | 생성자 |
| `final` 사용 | 어려움 | 가능 |
| 테스트 | 상대적으로 불편 | 편리 |
| 불변성 | 약함 | 좋음 |
| 의존성 명확성 | 낮음 | 높음 |
| 실무 추천 | △ | **◎** |

따라서 다음 방식을 권장합니다.

```java
@RequiredArgsConstructor
private final CategoryService categoryService;
```

## 9. 구현체가 2개일 때 — @Primary / @Qualifier

### 9.1 문제 상황

Service 구현체를 하나 더 만들어 봅니다.

```java
@Service
public class TestCategoryService
        implements CategoryService {

    // ...
}
```

그러면 Spring 입장에서 구현체가 두 개가 됩니다.

```text
CategoryService

   ↑            ↑

CategoryServiceImpl
TestCategoryService
```

Controller에서는 다음만 요구했습니다.

```java
private final CategoryService categoryService;
```

Spring 입장에서는 `어떤 CategoryService를 넣지?`라는 문제가 생깁니다. 이때 `@Primary` 또는 `@Qualifier`가 등장합니다.

### 9.2 `@Primary`

```java
@Service
@Primary
@RequiredArgsConstructor
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;

    // ...
}
```

그러면 Spring은 다음처럼 판단합니다.

```text
CategoryService 구현체가 2개인데

CategoryServiceImpl에 @Primary 있음

        ↓

CategoryServiceImpl 선택
```

### 9.3 `@Qualifier`

Bean에 이름을 부여합니다.

```java
@Service("dbCategoryService")
@RequiredArgsConstructor
public class CategoryServiceImpl
        implements CategoryService {

    private final CategoryMapper categoryMapper;
}
```

Controller에서 이름으로 지정합니다.

```java
@RestController
@RequestMapping("/api/categories")
public class CategoryController {

    private final CategoryService categoryService;


    public CategoryController(
        @Qualifier("dbCategoryService")
        CategoryService categoryService
    ) {

        this.categoryService =
                categoryService;
    }
}
```

그러면 Spring이 명확하게 해당 Bean을 선택합니다. 이 단계까지 직접 해보면 DI 개념이 상당히 명확해집니다.

## 10. Spring 내부 동작

애플리케이션 시작 시 대략 다음 과정을 거칩니다.

```text
@SpringBootApplication

        ↓

Component Scan

        ↓

@RestController 발견
@Service 발견
@Mapper 발견

        ↓

BeanDefinition 생성

        ↓

Bean 객체 생성

        ↓

생성자 분석

        ↓

필요한 Bean 검색

        ↓

의존성 주입

        ↓

ApplicationContext 관리
```

예를 들어 다음 코드에 대해,

```java
@RequiredArgsConstructor
public class CategoryController {

    private final CategoryService categoryService;
}
```

Spring 내부에서는 개념적으로 다음과 비슷한 일을 수행합니다.

```java
CategoryService service =
    applicationContext
        .getBean(CategoryService.class);

CategoryController controller =
    new CategoryController(service);
```

                         │
        ┌────────────────┼─────────────────┐
        │                │                 │

## 11. 학습 순서와 실습 과제

이 예제를 그냥 실행하는 것보다 다음 순서로 코드를 수정해보는 것이 훨씬 효과적입니다.

- [ ] 1. `CategoryController → CategoryService → CategoryMapper` 구조로 정상 실행합니다.
- [ ] 2. `@RequiredArgsConstructor`를 제거하고 직접 생성자를 작성합니다.
- [ ] 3. Field Injection인 `@Autowired` 방식으로 변경해 봅니다.
- [ ] 4. 다시 Constructor Injection으로 변경합니다.
- [ ] 5. `CategoryService` 구현체를 2개 만들어 오류를 확인합니다.
- [ ] 6. `@Primary`로 해결합니다.
- [ ] 7. `@Qualifier`로 해결합니다.
- [ ] 8. `ApplicationContext.getBean()`으로 실제 Bean을 직접 조회해 봅니다.

특히 **5~8번까지 실습하면 IoC/DI를 거의 확실하게 이해할 수 있습니다.**

### 반드시 확인해야 할 3가지

**① Controller**

```java
private final CategoryService categoryService;
```

**② Service**

```java
private final CategoryMapper categoryMapper;
```

**③ 어디에도 없는 코드**

```java
new CategoryServiceImpl()
new CategoryMapper()
```

그런데도 프로그램이 정상적으로 작동합니다. 이것이 Spring IoC/DI의 핵심입니다.

## 12. 최종 정리

> **Spring IoC는 객체의 생성과 생명주기를 Spring이 관리하는 것이고, DI는 Spring이 관리하는 Bean 사이의 의존관계를 연결해 주는 메커니즘입니다.**

그리고 현재 Spring Boot 실무에서는 다음 패턴을 기본으로 잡는 것이 좋습니다.

```java
@Service
@RequiredArgsConstructor
public class XxxService {

    private final XxxMapper mapper;
}
```

즉 **`private final` + 생성자 주입 + `@RequiredArgsConstructor`** 패턴입니다.
